01Panorama en 60 segundos

El módulo es la capa de seguridad transversal de SyncUT: decide quién entra, qué rol tiene, qué filas de la base de datos puede ver y deja constancia de lo que hace. Es el bloqueador del proyecto: ningún otro squad puede consultar datos protegidos sin él.

La idea central es que la seguridad no vive en el frontend, vive en la base de datos. Postgres, mediante Row Level Security (RLS), filtra cada consulta según el usuario que la hace. Aunque alguien manipule el navegador, la base no devuelve filas que no le corresponden.

Las cuatro piezas

PiezaDónde vivePara qué sirve
Identidadauth.users (Supabase) Credenciales, contraseña cifrada con bcrypt, confirmación de email y emisión del JWT. No la escribimos nosotros: la gestiona Supabase.
Perfil y rolpublic.profiles Extiende al usuario con nombre, teléfono, avatar y sobre todo role. Es la tabla que consultan todas las políticas de seguridad.
Permisospublic.role_permissions Catálogo RBAC: qué permiso concreto tiene cada rol (approve:justificacion, manage:users…).
Trazabilidadpublic.audit_logs y public.session_tokens Bitácora inmutable de acciones y registro de dispositivos/sesiones activas.
La frase para arrancar la exposición

«Nuestro módulo responde tres preguntas: ¿quién eres? (autenticación), ¿qué puedes hacer? (roles y RLS) y ¿qué hiciste? (auditoría). Las tres están resueltas a nivel de base de datos; la capa visual todavía va detrás.»

Cómo se conecta la aplicación a Supabase

Hay un único punto de entrada, para que ningún squad cree su propio cliente:

// packages/sdk/src/client.ts
import { createBrowserClient } from '@supabase/ssr';
import type { Database } from '@plataforma/types';

export const createSupabaseBrowserClient = () => {
  return createBrowserClient<Database>(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!
  );
};

Se usa así desde cualquier componente cliente: import { createSupabaseBrowserClient } from "@plataforma/sdk/client";

Punto que impresiona en la exposición

Los tipos de TypeScript de toda la base de datos están autogenerados por Supabase en packages/types/src/database.types.ts. Si alguien cambia una columna en SQL y no actualiza el código, el build falla. La base de datos y el código no pueden desincronizarse en silencio.

03La base de datos: cuatro tablas

Todo está en supabase/migrations/20240516000001_init_schemas.sql (132 líneas). Es el archivo que hay que abrir si te piden «enséñame el código».

3.1 · profiles — el perfil y el rol

CREATE TABLE public.profiles (
  id          uuid PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  email       text NOT NULL,
  full_name   text NOT NULL,
  role        text NOT NULL DEFAULT 'student',
  phone       text,
  avatar_url  text,
  created_at  timestamptz DEFAULT now(),
  updated_at  timestamptz DEFAULT now(),
  CONSTRAINT role_check CHECK (role IN ('student','teacher','tutor','admin','coordinator'))
);

Tres detalles que conviene saber explicar:

  • id es a la vez clave primaria y foránea hacia auth.users: relación 1 a 1. No puede existir un perfil sin usuario real.
  • ON DELETE CASCADE: si se borra el usuario en Supabase Auth, su perfil desaparece automáticamente. Cumplimiento de «derecho al olvido» sin código extra.
  • CHECK sobre role: es imposible insertar un rol inventado. La validación es del motor, no de la aplicación.

Índices: idx_profiles_email y idx_profiles_role, porque son las dos columnas por las que más se filtra.

3.2 · role_permissions — el catálogo RBAC

Tabla con UNIQUE(role, permission). Permite cambiar permisos sin recompilar: un permiso es una fila, no una línea de código. Ejemplos previstos: view:citas, approve:justificacion, manage:users, view:audit_logs.

3.3 · session_tokens — dispositivos activos

Guarda token (único), device_name, ip_address (tipo inet), expires_at y revoked_at. El truco de diseño: no se borra una sesión, se marca con revoked_at = now(). Así queda el histórico de quién cerró sesión y cuándo. Sirve para «cerrar sesión en todos los dispositivos» y para detectar accesos desde IPs extrañas.

3.4 · audit_logs — la bitácora inmutable

CREATE TABLE public.audit_logs (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     uuid REFERENCES public.profiles(id) ON DELETE SET NULL,
  action      text NOT NULL,        -- LOGIN, SIGNUP, UPDATE, DELETE...
  table_name  text NOT NULL,        -- tabla afectada
  record_id   uuid,                    -- fila afectada
  old_values  jsonb,                   -- antes
  new_values  jsonb,                   -- después
  ip_address  inet,
  user_agent  text,
  created_at  timestamptz DEFAULT now() NOT NULL
);

Por qué ON DELETE SET NULL y no CASCADE: si se borra un usuario, sus registros de auditoría sobreviven con user_id = NULL. Borrar una cuenta no puede borrar la evidencia de lo que hizo. Es el detalle que distingue una bitácora de verdad de un simple log.

Por qué old_values / new_values son jsonb: una sola tabla sirve para auditar cualquier otra tabla del sistema, sin importar sus columnas.

La lista de roles está duplicada en cuatro sitios. Si mañana se añade un rol guest, hay que tocar los cuatro o el sistema se rompe de forma silenciosa. Mejora propuesta: convertirlo en un ENUM de Postgres y que TypeScript lo derive del tipo autogenerado, con una sola fuente de verdad.

Asignación automática del rol: el trigger

Nadie asigna el rol a mano. Cuando Supabase crea un usuario, un trigger crea el perfil:

-- supabase/migrations/20260523000001_sync_auth_profiles.sql
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS trigger AS $$
BEGIN
  INSERT INTO public.profiles (id, email, full_name, role)
  VALUES (
    new.id,
    new.email,
    COALESCE(new.raw_user_meta_data->>'full_name', 'Nuevo Usuario'),
    COALESCE(new.raw_user_meta_data->>'role', 'student')
  );
  RETURN new;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW EXECUTE FUNCTION public.handle_new_user();

Dos palabras clave que te pueden preguntar:

  • SECURITY DEFINER: la función se ejecuta con los privilegios de quien la creó, no de quien la dispara. Es lo que permite escribir en profiles aunque el usuario nuevo todavía no tenga permisos.
  • COALESCE: toma el primer valor no nulo. Si el registro no manda rol, queda 'student'. El privilegio mínimo es el valor por defecto.

El administrador maestro

La migración 20260606000001_set_master_admin.sql reescribe el trigger para que un correo concreto (jassiel.rr1502@gmail.com) reciba siempre role = 'admin', y además hace un UPDATE por si el perfil ya existía. Garantiza que el proyecto nunca se quede sin administrador.

Observación honesta sobre esta decisión

Es un correo quemado en el código SQL. Funciona para la etapa académica del proyecto, pero en producción el administrador debería promoverse desde una tabla de configuración o una variable de entorno, no desde una migración versionada en el repositorio.

05RLS: la seguridad que vive en la base de datos

Row Level Security es el corazón del módulo y el mejor argumento técnico de la exposición. Es un filtro WHERE invisible que Postgres añade a toda consulta, venga de donde venga.

Se activa tabla por tabla:

ALTER TABLE public.profiles         ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.audit_logs       ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.session_tokens   ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.role_permissions ENABLE ROW LEVEL SECURITY;

La función clave es auth.uid(): devuelve el UUID del usuario extraído del JWT firmado. No se puede falsificar desde el navegador, porque la firma se verifica en el servidor.

Las seis políticas implementadas

PolíticaOperaciónRegla en una línea
profiles_self_viewSELECTVes tu propio perfil; los admin ven todos.
profiles_update_ownUPDATEEditas tu propio perfil; los admin editan cualquiera.
audit_logs_viewSELECTVes tus propios eventos; los admin ven el histórico completo.
audit_logs_no_deleteDELETEUSING (false) — nadie borra nunca. Inmutabilidad real.
session_tokens_viewSELECTVes tus dispositivos; los admin ven todos.
role_permissions_viewSELECTUSING (true) — el catálogo de permisos es público para usuarios autenticados.

La política que hay que leer en voz alta

CREATE POLICY "audit_logs_view"
  ON public.audit_logs FOR SELECT TO authenticated
  USING (
    user_id = auth.uid()                      -- tus propios eventos
    OR EXISTS (
      SELECT 1 FROM public.profiles
      WHERE id = auth.uid() AND role = 'admin'   -- o eres admin
    )
  );

CREATE POLICY "audit_logs_no_delete"
  ON public.audit_logs FOR DELETE TO authenticated
  USING (false);   -- ni el admin puede borrar la evidencia

Qué demostrar: un alumno que ejecute SELECT * FROM audit_logs no recibe un error de permisos: recibe cero filas. La base de datos no revela siquiera que existan otros registros.

Diferencia de USING y WITH CHECK

USING filtra las filas que puedes leer o tocar. WITH CHECK valida las filas que intentas escribir. En profiles_update_own están los dos, para que nadie lea su propia fila y la convierta en la de otro usuario.

Hueco de seguridad detectado — mencionarlo suma puntos

Las políticas profiles_self_view y profiles_update_own usan auth.uid() = id OR role = 'admin'. Ese role es el de la fila que se está evaluando, no el del usuario que consulta. Efecto real: cualquier usuario autenticado puede leer y modificar los perfiles cuyo rol sea admin. Es decir, un alumno podría editar el perfil del administrador.

Además, profiles_update_own no impide que un usuario se cambie su propio role a admin — el documento de diseño lo da por protegido, pero la política no lo implementa.

Corrección: usar la subconsulta EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role = 'admin'), igual que en audit_logs_view, y añadir un WITH CHECK que congele la columna role salvo para administradores.

06Registro y login: diseño frente a implementación actual

Aquí está el punto más importante de honestidad de la exposición: el diseño del flujo está completo y documentado, pero el código actual de las pantallas es todavía una maqueta funcional que no habla con Supabase.

6.1 · Flujo de registro diseñado

  1. El usuario llena nombre, correo y contraseña. Validación en el navegador.
  2. Se llama a supabase.auth.signUp({ email, password, options: { data: { full_name } } }).
  3. Supabase crea la fila en auth.users, cifra la contraseña con bcrypt y envía correo de confirmación.
  4. El trigger handle_new_user() dispara y crea el perfil con rol student.
  5. Se registra el evento SIGNUP en audit_logs.
  6. El usuario confirma su correo y ya puede iniciar sesión.

6.2 · Flujo de login diseñado

  1. supabase.auth.signInWithPassword({ email, password }) valida contra auth.users.
  2. Si es correcto: se emite el JWT, se inserta la fila en session_tokens (dispositivo, IP, expiración) y se guarda una cookie HttpOnly.
  3. Se registra LOGIN en audit_logs.
  4. Si falla: se registra LOGIN_FAILED con IP y motivo; a partir de tres intentos en 15 minutos se bloquea temporalmente.
  5. En cada petición posterior, el middleware valida el JWT y RLS filtra los datos.

6.3 · Lo que hace el código hoy

apps/web/app/(auth)/login/page.tsx — componente "use client" con formulario, mostrar/ocultar contraseña, «recordar sesión» y manejo de errores. La validación es una maqueta:

// Mock validation to match the mockup error state
if (password !== "hunter2") {
  setErrorMsg("Contraseña incorrecta. Por favor intente de nuevo.");
  return;
}

window.localStorage.setItem("syncut_beta_session", JSON.stringify({
  email: cleanUsername,
  role: cleanUsername.toLowerCase().includes("admin") ? "admin" : "student",
  loggedAt: new Date().toISOString(),

apps/web/app/(auth)/signup/page.tsx — valida campos obligatorios, longitud mínima de 8 caracteres, coincidencia de contraseñas y aceptación de términos; incluye un medidor visual de fuerza. Después guarda el usuario en localStorage["syncut_beta_users"] y redirige al login.

Cómo decirlo sin que suene mal

«Las pantallas de login y registro están construidas contra la maqueta de diseño y usan localStorage como sesión temporal, para que los otros cinco squads pudieran navegar y desarrollar sus módulos sin esperarnos. La contraseña de demostración es literal y la sesión vive solo en el navegador: no es un mecanismo de seguridad, es un andamio. El siguiente paso es sustituir esas dos funciones por signUp y signInWithPassword; la base de datos ya está lista para recibirlas.»

Detalle técnico que conviene tener claro

En la maqueta, el rol se decide con email.includes("admin"), en el navegador. Eso significa que hoy cualquiera podría escribir admin@loquesea.com y obtener rol admin en el estado local. No otorga acceso a datos reales, porque RLS sigue vigente en Supabase y el JWT nunca se emite; el efecto se limita a la interfaz.

Los validadores «de verdad» ya existen y están listos para conectarse, en packages/shared/src/validators.ts:

validateEmail(email)     // formato + rechazo de patrones de inyección ( ; -- /* )
validatePassword(pass)   // 8+ caracteres, mayúscula, minúscula y número
validateRole(role)       // pertenencia a VALID_ROLES

La función de escritura (especificada, aún no creada)

// apps/web/app/(auth)/lib/auditLog.ts  ← archivo por implementar
export async function logAudit(entry: AuditLogEntry) {
  const { data, error } = await supabase.from('audit_logs').insert({
    user_id: entry.userId,     action:     entry.action,
    table_name: entry.tableName, record_id: entry.recordId,
    old_values: entry.oldValues, new_values: entry.newValues,
    ip_address: entry.ipAddress, user_agent: entry.userAgent,
  });
  if (error) console.error('Audit log failed:', error);
  // No se lanza excepción: auditar nunca debe romper la operación del usuario
  return data;
}

Esa última decisión de diseño es importante y conviene subrayarla: si falla la auditoría, la operación del usuario continúa. Se registra el problema, pero no se rompe la experiencia.

Lo que sí está funcionando: la lectura en tiempo real

El Panel de Gobernanza consume audit_logs y los convierte en un feed de actividad.

apps/web/components/modules/executive-dashboard/live-data.ts — consulta inicial:

await supabase
  .from("audit_logs")
  .select("user_id, action, table_name, created_at", { count: "exact" })
  .order("created_at", { ascending: false })
  .limit(30);

…/executive-dashboard-page.tsx — suscripción a Supabase Realtime, que empuja cada nuevo registro al feed sin recargar la página:

supabase.channel("executive-audit-stream")
  .on("postgres_changes",
     { event: "INSERT", schema: "public", table: "audit_logs" },
     (payload) => { /* añade la actividad al feed en vivo */ })
  .subscribe();

Hay además funciones auxiliares que enriquecen cada evento: inferModule() deduce a qué módulo pertenece según la tabla, inferAction() clasifica el tipo de acción e inferImpact() asigna un nivel de impacto (Alto / Medio / Bajo). Los datos se pueden exportar a CSV con toCsvReport().

El resumen de una frase

«La tubería de auditoría está construida de la mitad hacia adelante: la tabla existe, es inmutable, se lee y se transmite en vivo al panel ejecutivo. Lo que falta es el emisor —logAudit()— conectado a los puntos críticos. Es trabajo de conexión, no de arquitectura.»

Todo el sistema degrada con elegancia: si no hay NEXT_PUBLIC_SUPABASE_URL ni NEXT_PUBLIC_SUPABASE_ANON_KEY, las funciones devuelven datos de respaldo y marcan hasLiveSource: false en lugar de fallar.

11Preguntas que te van a hacer (con respuesta)

¿Dónde se guardan las contraseñas?
Nunca en nuestras tablas. Viven cifradas con bcrypt en auth.users, que administra Supabase. Nuestra tabla profiles no tiene ni puede tener una columna de contraseña.
¿Qué pasa si alguien modifica el JavaScript del navegador para ponerse rol admin?
Cambiaría lo que ve en pantalla, nada más. El rol que importa se lee de profiles y las políticas RLS lo evalúan del lado del servidor usando auth.uid(), que sale del JWT firmado. Sin JWT válido, la base devuelve cero filas.
¿Por qué duplicar el correo en profiles si ya está en auth.users?
Es denormalización deliberada. auth.users está en un esquema interno de Supabase al que no se puede hacer JOIN libremente desde el cliente. Tener el correo en profiles evita una llamada extra en cada consulta y permite indexarlo.
¿Cómo garantizan que un log no se pueda alterar?
Con la política audit_logs_no_delete que devuelve USING (false): ningún rol autenticado puede borrar. Tampoco existe política de UPDATE, y en RLS lo que no está permitido explícitamente está prohibido. Además created_at lo pone el servidor, no el cliente.
¿Y si borran un usuario, se pierde su auditoría?
No. La clave foránea es ON DELETE SET NULL: los eventos permanecen con user_id nulo. Es una decisión de diseño consciente y es lo que exige cualquier norma de cumplimiento.
¿El login ya funciona contra la base de datos?
Todavía no. Las pantallas están terminadas y el esquema está listo, pero la validación actual es una maqueta con localStorage que construimos para desbloquear a los otros cinco squads. La sustitución son dos llamadas: signUp y signInWithPassword.
¿Qué es SECURITY DEFINER y por qué lo usan?
Hace que la función se ejecute con los privilegios de quien la creó. Sin eso, el trigger no podría insertar en profiles en el instante en que nace el usuario, porque todavía no tiene permisos propios.
¿Cuál es la diferencia entre roles y permisos?
El rol es la etiqueta del usuario y vive en profiles.role. El permiso es la acción concreta y vive en role_permissions. Separarlos permite cambiar qué puede hacer un docente sin tocar el código ni migrar usuarios.
¿Qué falta y cuánto cuesta?
Cinco cosas: corregir dos políticas RLS, conectar Supabase Auth a las dos pantallas, crear el middleware, implementar logAudit() y poblar role_permissions. Todo es trabajo de integración sobre cimientos que ya existen; no hay que rediseñar nada.
¿Por qué no usaron NextAuth / JWT propio?
Porque Supabase Auth ya emite un JWT que Postgres entiende de forma nativa mediante auth.uid(). Esa integración es la que permite que RLS funcione. Con un sistema de autenticación externo tendríamos que replicar toda la autorización en la capa de aplicación, que es justo lo que queríamos evitar.
